Context

What it is

CAR Superapp has been worked through as a target operating system for an auto workshop: staff runs the work order, customers see status and evidence, and a network manages branches, roles, payments, documents and audit in one model.

The problem it solves

When intake, photos, extra work, customer consent and payment live in separate chats, a workshop loses trust and margin. A network adds the risk of branch data leakage and ambiguous authority.

Architecture

The architecture contract proposes a responsive PWA and API as a modular monolith. The implementation plan uses forced RLS for tenant/branch boundaries, Prisma for the typed model, Redis/BullMQ for background work and outbox/idempotency for integrations.

Why this architecture

At this stage a modular monolith gives transactional integrity and lower operational cost while preserving domain boundaries for later extraction. RLS duplicates application checks where a mistake would be especially expensive.

Evidence

Strengths

The project starts with scope, threats, payment/media/scheduling state machines, migrations and operations — not a decorative dashboard. Its target is at least 50 branches per tenant without data crossover.

What it proves

The case demonstrates large-product work before code: discovery, ADRs, UX information architecture, threat modelling, data design, API contracts and measurable acceptance/release gates.

Quality · QA

How quality was engineered

QA is specified as an executable implementation plan: negative cross-tenant/branch RLS cases, contract tests, lint, strict typecheck, dependency audit, build and release gates. These are acceptance criteria; a passed CI run or production deployment is not claimed.
